# Audit EWAT — 2026-06-10 (data → modèle → résultats)

Audit complet du projet, trois couches : données, modèles, évaluation/résultats. Il s'inscrit
**après** l'audit méthodologique du 2026-05-26 (38 fixes) et les limites documentées
(`docs/limitations.md` L2.1–L7.6, STATUS.md L1–L17) — l'objectif est ce qui **reste**, en
distinguant explicitement « nouveau » de « déjà documenté ». Toutes les références fichier:ligne
citées ont été vérifiées dans le code au 2026-06-10 (commit `58f53ea`) ; les points rapportés par
exploration mais non re-vérifiés sont marqués *(à confirmer)*. Une section finale liste les faux
positifs écartés pendant l'audit lui-même.

Contexte temporel : la collecte v5 Train Ticket tourne sur la VM (~720 épisodes, 41 services).
Les points marqués **P0** ont une fenêtre d'opportunité **avant le premier build v5**.

---

## 1. Résumé exécutif

**40 points d'amélioration** consolidés : 3 critiques, 17 majeurs, 20 mineurs.

| Couche | Critique | Majeur | Mineur | Total |
|---|---|---|---|---|
| Données (D1–D12) | 1 | 6 | 5 | 12 |
| Modèles (M1–M15) | 0 | 7 | 8 | 15 |
| Évaluation (E1–E13) | 2 | 4 | 7 | 13 |

### Les 5 verdicts fondamentaux

1. **E1 — Aucune comparaison à l'état de l'art publié.** Pas une ligne d'USAD, TranAD, GDN,
   Anomaly Transformer (détection d'anomalies multivariée) ni Eadro/DeepTraLog (typing/RCA
   microservices) dans le repo. Le headline B2 = 0.920 est honnête mais **non positionnable** :
   un relecteur demandera « comparé à quoi ? ». C'est le plus gros trou pour une publication, et
   ewat_v5 (potentiellement public) est exactement le véhicule pour le combler.
2. **D1 — Schéma de features fragmenté 17 vs 18.** `SIGNAL_DIM = 17` dans
   `src/telemetry/feature_names.py:48` (avec assert), mais le schéma v5 (18 features) vit
   uniquement dans `v5/collect/build_features_v5.py:71-80` et `scripts/validate_v5.py:30-31`.
   Aucun registre versionné partagé ; tous les modules `src/ewat/` supposent 17. À régler
   **avant** le premier build v5.
3. **E2 — Calibration des probabilités jamais évaluée.** Aucun Brier score, ECE ni reliability
   curve dans le repo. Le point opérationnel recommandé (seuil p = 0.7, FA = 8.3 %) repose sur
   des probabilités LR brutes dont personne ne sait si p = 0.7 signifie 70 %.
4. **E5 — La variance du split n'a jamais été mesurée.** Les 10 graines de Phase H tournent sur
   le *même* split 270/60/45. L'IC [0.878, 0.956] de B2 capture le bootstrap intra-split, pas la
   variance inter-split (déjà noté L2.5/L6.1, jamais actionné — v5 le permet enfin avec
   30 reps/scénario).
5. **D2+D3 — La gestion des NaN efface un signal.** Deux stratégies d'imputation incompatibles
   (v4 post-hoc, v5 inline), et surtout : le masque de missingness (`signal_mask.npz`) est créé
   à chaque épisode mais **jamais exploité par les modèles** — alors que T ≈ 20-25 % NaN
   *structurel sur crash* signifie que la missingness est elle-même une feature discriminante du
   type de panne.

## 2. Points transverses fondamentaux

Avant les fixes incrémentaux, trois choix fondateurs à acter (pas seulement documenter) :

**T1 — Assumer le pipeline opérationnel sans STGCN.** C1 a montré 0.863 < B2 = 0.920 : le STGCN
n'apporte rien à la chaîne prédictive. STATUS l'acte en « Option B docs », mais le code des
expériences v5 va, par inertie, réentraîner encoder→siamois→precursor en chaîne. Décision à
prendre *avant* les analyses v5 : la chaîne prédictive officielle est
`S(t) → instance norm → LR-OvR`, le STGCN est un module *clustering + ontologie* uniquement.
Cela divise le coût de calcul des analyses v5 et simplifie le rapport.

**T2 — Une seule cible d'évaluation honnête.** Les évaluations sur labels EWAT (circulaires,
L9/A1) coexistent encore partout avec les évaluations Chaos Mesh. Pour v5 : labels Chaos Mesh
(et bugs F) comme cible primaire *partout*, labels EWAT relégués explicitement en diagnostic
interne du clustering.

**T3 — Acter K.** STATUS (Phase K) recommande « K = 10 fixe ou HDBSCAN » depuis le 2026-05-26 ;
rien n'est implémenté (`src/ewat/typing/clustering.py` propose silhouette argmax — documenté
fragile à la ligne 135-136 — et gap Tibshirani, en désaccord 6/10). Sur v5 (22 scénarios, n
plus grand), le choix doit être pris **avant** la première analyse, sinon toutes les comparaisons
multi-graines hériteront de l'instabilité K ∈ [9, 15].

## 3. Couche données

### D1 — Schéma features fragmenté 17/18 ⚠ CRITIQUE · nouveau · effort M · **P0**
`src/telemetry/feature_names.py:48` (`SIGNAL_DIM = 17`) vs `v5/collect/build_features_v5.py:71-80`
(`FEATURE_NAMES` 18, `N_FEATURES = 18`) vs `scripts/validate_v5.py:30-31` (recopie). Trois
définitions indépendantes, aucune source de vérité versionnée. `src/ewat/encoder/dataset.py`,
`assemble_dataset.py`, `validate_dataset.py` supposent 17. Lancer un outil v4 sur des features
v5 échoue tard ou silencieusement.
**Piste** : registre `src/telemetry/feature_catalog.py` versionné (v4 : 17, v5.1 : 18) + un
`features_manifest.json` écrit par le builder dans chaque feature root, lu par dataset/validate.

### D2 — Imputation fragmentée v4/v5, provenance non persistée · majeur · nouveau · effort M
v4 : `scripts/impute_features.py` post-hoc (médiane épisode + fallback médianes train pour
`trace_depth`/`disk_io`, ffill/bfill pour les dims sparses — lignes 11-66). v5 : imputation
inline dans `build_features_v5.py:98-146`. Deux stratégies, zéro module commun, et la stratégie
appliquée n'est pas persistée dans `metadata.json` (seul `signal_nan_ratio` l'est,
`serialization.py:179`). Comparer des résultats v4/v5 devient une comparaison de stratégies
d'imputation non documentée.
**Piste** : module `src/telemetry/imputation.py` unique + champ `imputation` dans metadata.

### D3 — Le masque de missingness existe mais les modèles l'ignorent · majeur · nouveau · effort M
`src/utils/serialization.py:83-86` crée `signal_mask.npz` pour chaque épisode ; seuls
`validate_dataset.py:63` et `ontology/synthesis.py:110` le lisent. Encoder, typing, precursor
travaillent sur le signal imputé. Or T ≈ 20-25 % NaN est *structurel sur crash* (STATUS) : la
missingness est corrélée au type de panne, et l'imputation l'efface.
**Piste** : concaténer le masque (ou un ratio de missingness par modalité) comme features
d'entrée du LR-OvR — expérience à 1 journée, potentiellement du gain gratuit sur B2.

### D4 — Split stratifié opt-in · majeur · nouveau (choix post-audit) · effort S · **P0**
`scripts/assemble_dataset.py:546-552` : `--stratified` reste opt-in « to avoid breaking existing
scripts », avec warning bruyant sinon (ligne 452-454). C'est précisément ce défaut qui a produit
ewat_v4 inutilisable (4 scénarios absents du train). Le coût de casser un script legacy est
inférieur au coût d'un dataset v5 mal splitté.
**Piste** : inverser le défaut (`--stratified` par défaut, `--temporal` opt-in) + erreur (pas
warning) si un scénario est absent du test.

### D5 — Held-out v5 non intégré à l'assemblage · majeur · nouveau · effort S · **P0**
`scripts/enforce_heldout_v5.py` est un correctif post-hoc ; `assemble_dataset.py` n'a aucune
notion de held-out (grep « held » : zéro occurrence). Si l'étape est oubliée, les 3 scénarios
chaos held-out + bugs F fuient dans le train et les évaluations open-set v5 sont invalides.
**Piste** : option `--held-out-scenarios` (ou lecture d'une colonne de labels.parquet) dans
`assemble_dataset.py`, qui route ces épisodes vers test et le consigne dans `dataset.json`.

### D6 — Tests du pipeline data quasi absents · majeur · étend L7.4 · effort M · **P0** (volet v5)
`tests/unit/scripts/` = 2 fichiers (`test_record_episode_quality.py`,
`test_assemble_index_columns.py`). Rien sur : la logique de labeling 4 régimes de
`build_features.py` (la partie la plus subtile du pipeline), la grille temporelle, `validate_dataset`,
`impute_features`, ni **aucun test du pipeline v5** (`build_features_v5`, `validate_v5`,
`enforce_heldout_v5`) alors qu'il va produire le dataset principal du projet.
**Piste minimale** : un test golden sur un mini-dump v5 synthétique (3 services, 5 steps) qui
verrouille shapes, labels de régime et imputation.

### D7 — Duplication collectors/extractors sans test d'équivalence · majeur · nouveau · effort M
`src/telemetry/collectors/prometheus_collector.py` (~690 lignes) et
`src/telemetry/extractors/prom_file.py` (héritage + override `_query_all`). La logique
d'agrégation pod→service vit dans le parent, mais aucun test ne garantit qu'un même dump produit
les mêmes features en ligne et hors ligne. Une correction future dans l'un divergera
silencieusement de l'autre. Même schéma pour traces/logs.
**Piste** : test golden online-vs-offline sur un dump enregistré.

### D8 — `metric_window_s` inutilisé, alignement M/T/L non validé · mineur · **connu (L2.4)** 
`scripts/build_features.py:171` (« unused at the moment ») ; le fix 2.1 ajoute un warning
(lignes 310-319) mais ne valide toujours pas l'alignement des fenêtres entre modalités. Reste
en l'état pour v4 ; à trancher (implémenter ou supprimer le paramètre) pour v5.

### D9 — Quality gate Phase 1 partiel · mineur · **connu (L2.6)**
`record_episode.py` : gate sur n_traces ≥ 5 et n_lines > 0, sans contrôle de structure des logs.
Conséquence vécue : 32 épisodes nan_L = 1.00 (panne Loki) découverts seulement en Phase 3.
Pour v5, le `health_monitor.py` mitige côté collecte mais le gate structurel manque toujours.

### D10 — Couverture par service jamais vérifiée au niveau dataset · mineur · nouveau · effort S
`validate_v5.py:44-45` vérifie bien la shape (41, 18) par épisode (bon point), mais le
commentaire « diverse scenarios cover all services at dataset level » n'est validé par rien.
Avec 41 services et ~22 scénarios ciblés, certains services peuvent n'être *jamais* la cible
d'un chaos — ce qui borne ce que le typage peut apprendre sur eux.
**Piste** : rapport de couverture service × scénario dans `validate_v5` (mode dataset).

### D11 — Incohérence doc : §0.5 du plan v5 dit « 17 features » · mineur · nouveau · effort S · **P0**
`docs/dataset_v5_plan.md` §0.5 (« Lean enrichi, 17 features ») n'a pas suivi le schéma v5.1
final à 18 features (STATUS). À corriger avant que quelqu'un code contre le plan.

### D12 — Provenance de build non persistée · mineur · nouveau · effort S
`metadata.json` ne contient ni la version du builder, ni la grille temporelle effective, ni la
stratégie d'imputation (cf. D2). La reproductibilité d'un épisode buildé dépend de la mémoire
du projet.

## 4. Couche modèles

### M1 — ε_drift : calibré sur v3, dupliqué en dur · majeur · instance de L7.3 · effort S
`configs/default.yaml:63` (0.5226, Youden sur v3, **AUC = 0.60** — discrimination déjà faible à
la calibration) ET recopié `src/ewat/alerts/assembler.py:58` (`DEFAULT_DRIFT_EPSILON = 0.5226`).
Jamais recalibré par défaut pour v4/v5 (la recalibration C5 est restée dans l'expérience
`h2_lookthrough_v4`). Tout run AlertAssembler sur v5 utilisera un seuil calibré sur Online
Boutique 2026-04.
**Piste** : supprimer la constante dupliquée, exiger ε dans la config, recalibrer sur v5.

### M2 — Reset de σ à la recalibration : l'échelle du MMD² change, pas ε · majeur · nouveau · effort S
`src/ewat/drift/detector.py:~190-193` : `_recalibrate()` invalide `_sigma` (et W, b) → le σ de
la bandwidth est re-fitté sur la nouvelle fenêtre. Or l'échelle du MMD² dépend de σ, et
ε_drift reste fixe : la sémantique du seuil n'est plus comparable avant/après recalibration.
Cohérent avec H2b (« le DD déclenche partout »).
**Piste** : σ fixé à la calibration (ou EMA), ou re-normaliser le MMD² par sa distribution nulle
locale (permutation rapide) plutôt que de comparer à un ε absolu.

### M3 — Fenêtres drift 5/5 en dim 17 : estimateur MMD² à variance énorme · majeur · recoupe L4.6
`assembler.py:60-61` (`WINDOW_REF = WINDOW_CUR = 5`). Cinq points en dimension 17 : le MMD²
empirique est essentiellement du bruit, d'où drift % = 0.51–1.00 même sur anomalies pures (H2b).
v5 (épisodes plus longs) permet enfin des fenêtres 15-20.
**Piste** : fenêtres dimensionnées sur v5 + remplacement du seuil unique par un test séquentiel
(CUSUM / Page-Hinkley sur la statistique MMD²) — c'est la seule voie crédible restante pour
sauver quelque chose de l'étape 0 après H2a FAIL.

### M4 — Pas de self-loops dans la convolution spatiale · majeur · nouveau · effort S
`src/ewat/encoder/stgcn.py:65-70` : normalisation symétrique D^{-1/2} A D^{-1/2} **sans A+I**,
puis `matmul(a_norm, x)` (ligne 84-88) : un nœud sans arêtes ne reçoit *aucun* message — il ne
reste que le biais. Combiné au problème documenté des graphes précoces vides (warning
empty_graphs de build_features), des timesteps entiers traversent la couche spatiale en perdant
le signal de tous les nœuds.
**Piste** : Â = D̃^{-1/2}(A+I)D̃^{-1/2} (Kipf & Welling standard) — une ligne, à réévaluer sur H1.

### M5 — Pas de validation shape signal/adjacency au forward · mineur · nouveau · effort S
`stgcn.py` forward : seule `lengths >= 1` est vérifiée (ligne 279). Un décalage (T, N) entre
signal et adjacency broadcast ou crash de façon opaque.

### M6 — Early stopping siamois sur la mauvaise métrique · majeur · levier non actionné de L10 · effort S
`experiments/typing/train.py:368-381` : le checkpoint est sélectionné sur la *val loss
contrastive* (patience 15), alors que la métrique cible est la silhouette. Le surentraînement
best_epoch ≈ 3 est documenté (L10, Phase H) mais le critère de sélection — le levier le plus
direct — n'a jamais été changé.
**Piste** : sélectionner le checkpoint sur silhouette val (nearest-centroid, déjà implémentée
dans le script ligne 415) ; coût quasi nul, à faire avant les entraînements v5.

### M7 — margin = 2.0 sature la hinge sur la sphère unité · mineur · nouveau · effort S
`src/ewat/typing/siamese.py:20` (docstring : « d ∈ [0, 2] so margin=1.0 (half the range) ») et
ligne 63 (`F.normalize`). Avec margin = 2.0 (Phase G), *toute* paire négative non strictement
antipodale a une perte > 0 : la hinge ne se désactive jamais et la loss dégénère en répulsion
uniforme. Empiriquement ça a marché (sil 0.838), mais c'est un régime dégénéré non compris —
le gain venait peut-être uniquement de la répulsion constante, pas de la marge.
**Piste** : sweep margin ∈ {1.5, 1.8, 2.0} sur v5 + documenter l'interprétation.

### M8 — K : recommandation Phase K non implémentée · majeur · **connu (STATUS)** · effort S/M · cf. T3
`clustering.py:135-139` documente lui-même la fragilité du argmax silhouette ; gap Tibshirani
n'est d'accord que 4/10. K fixe ou HDBSCAN : décidé sur le papier, absent du code.

### M9 — Pas de modèle nul pour la silhouette · mineur · nouveau · effort S
Aucune comparaison de la silhouette obtenue à une référence nulle (labels permutés, ou données
gaussiennes de même dimension). H1 « sil ≥ 0.3 » serait plus solide avec un
Δ(sil − sil_null) et son IC.

### M10 — TE cluster-level : le chemin pré-moyenné reste le défaut · mineur · **connu (L3.2)**
`experiments/ontology/build.py:110` appelle `compute_causal_relations` (pré-moyennage,
`causal.py:372-373`, biais documenté en commentaire) alors que l'estimateur hiérarchique
service-level existe (`causal.py:476+`). À basculer pour v5 (épisodes plus longs ⇒ T ≥ 5d
atteignable par épisode).

### M11 — Garde-fous TE en warning, résolution p limitée · mineur · nouveau · effort S
`causal.py:306-310` : T < 85 en multivarié ⇒ warning, pas erreur. `n_permutations = 100` ⇒
résolution p = 1/101, grossière sous BH-FDR.
**Piste** : ValueError (avec flag d'override) + 500 permutations par défaut.

### M12 — k* sans lissage · mineur · partiellement connu (C-5) · effort S
`k_stability_check` existe (`precursor/model.py:221`) mais le choix final reste l'argmax. Sur des
courbes AUROC(k) plates, k* saute de ±1-2 steps entre runs.
**Piste** : règle « k le plus court à ΔAUROC < 0.02 du max » (parcimonie + précocité).

### M13 — Open-set : Mahalanobis implémenté mais jamais comparé · majeur · axe C ROADMAP · effort M
OpenMax unknown AUROC = 0.55 (connu, L12) ; `tail_size_ratio` existe (`openmax.py:84-88`) mais
le défaut reste tail fixe = 20 sur des classes à n_c ≈ 3 ; et `src/ewat/openset/mahalanobis.py`
existe **sans aucune évaluation comparative** dans `experiments/`.
**Piste** : rejouer le protocole LOSO C3 avec {openmax, mahalanobis, energy/kNN-OOD} — les
held-out v5 (batch A + bugs F) sont le terrain idéal.

### M14 — Aucune politique d'alerte différenciée pendant drift_flag · majeur · nouveau · effort M
`assembler.py:313-314` : pendant un drift, les alertes sortent à pleine puissance avec
`drift_flag=True`, filtrage délégué à l'appelant. Le look-through sur le *signal* est un
invariant du projet (règles impératives) — mais rien n'interdit une politique au niveau
*décision* : confirmation sur k steps consécutifs quand drift_flag est actif, ou seuil par
cluster. C'est la cause directe de FA drift = 100 % aux seuils 0.3–0.5.
**Piste** : politique de confirmation configurable dans AlertAssembler (sans toucher au signal),
évaluée sur la grille seuil × confirmation.

### M15 — Cohérence scaler train/inférence non vérifiée · mineur · nouveau · effort S
`assembler.py:300-311` applique un scaler chargé séparément des checkpoints ; aucune empreinte
(hash des paramètres du scaler) n'est stockée dans les checkpoints encoder/siamois pour
détecter un mismatch.

## 5. Couche évaluation / résultats

### E1 — Zéro baseline état de l'art ⚠ CRITIQUE · nouveau · effort L · P3 (axe B)
Vérifié : aucun hit USAD/TranAD/GDN/Anomaly Transformer dans le repo. Les seules baselines sont
maison (B0–B4, z-score). Pour publier ewat_v5, il faut au minimum 2 méthodes publiées évaluées
avec le même protocole (cible Chaos Mesh, PR-AUC + AUROC, IC bootstrap). USAD et TranAD ont des
implémentations publiques adaptables en quelques jours chacune.

### E2 — Calibration jamais évaluée ⚠ CRITIQUE · nouveau · effort S · **P1**
Vérifié : aucun `calibration_curve`/Brier/ECE dans le repo ; le seul `CalibratedClassifierCV`
(`precursor/model.py:89`) sert à rendre le SVC probabiliste, pas à évaluer. Toute la table
opérationnelle (seuils 0.3→0.7, FA, lead-time) suppose des probabilités interprétables.
**Piste** : script `experiments/calibration/eval.py` — reliability curves + Brier + ECE par
cluster, et recalibration isotonique/Platt si ECE > 0.1. Une journée de travail, gros gain de
crédibilité opérationnelle.

### E3 — PR-AUC non généralisé · majeur · nouveau · effort S · **P1**
Présent dans `chaos_mesh_target.py:35,101` (fix M-6) et en courbe dans `experiments/alerts/` ;
**absent** de l'évaluation H3 (`experiments/precursor/train.py`), du multiseed, des ablations et
du LOSO. Avec n_pos = 3–8, l'AUROC seule est optimiste (M-6 l'a déjà montré : PR-AUC ∈
[0.166, 1.000] par scénario là où le macro-AUROC affiche 0.920).
**Piste** : ajouter PR-AUC partout où un AUROC est reporté ; standard pour les analyses v5.

### E4 — Lead-time sans intervalle de confiance · majeur · nouveau · effort S · P2
`experiments/alerts/results.md` ligne 5 : « Bootstrap CIs : non ». La table seuil × lead existe
mais le chiffre défendu (« 3.0 min au seuil 0.7 ») est un point estimé sans IC, et il n'y a pas
de courbe lead-time vs FA permettant de répondre à « quel lead pour FA < 5 % ? ».

### E5 — Variance inter-split non mesurée · majeur · **connu (L2.5, L6.1)** · effort M · **P1**
Multi-seed Phase H = 10 graines, même split. Jamais actionné. v5 (30 reps/scénario, 3 runners)
permet un k-fold stratifié par scénario × rep propre — à inscrire dans le protocole v5 *avant*
la première analyse, pas après.

### E6 — Pas de baseline oracle · mineur · nouveau · effort S
Aucune borne supérieure (modèle entraîné train+val+test, ou bayes proxy) : impossible de dire si
le gap 0.920 → 1.0 est du bruit irréductible ou de la marge de progression.

### E7 — Cadre statistique hétérogène · mineur · partiellement connu (L3.6) · effort S · P2
Student (H2), Wilcoxon (ablation), Fisher (H2b), bootstrap BCa (H3), McNemar absent — sans
section « quel test pour quelle comparaison » dans `docs/evaluation_protocol.md`. L3.6 note déjà
le t-test sur indicatrices binaires.

### E8 — Filtre n_pos ≥ 5 non appliqué uniformément · mineur · nouveau · effort S
Le filtre « clusters reportables » (C-5, power analysis) est appliqué en Phase G mais pas dans
tous les tableaux (multiseed, ablations) ; le macro-AUROC y mélange clusters reportables et
non concluants à poids égal.

### E9 — Robustesse aux NaN non quantifiée · majeur · nouveau · effort S · **P1**
Aucune courbe AUROC = f(taux de NaN injecté). Critique pour la prétention early-warning en
production : on sait que T ≈ 20-25 % NaN structurel, on ne sait pas où le modèle s'effondre.
Complémentaire de D3 (le masque comme feature).

### E10 — Edge cases non testés · mineur · recoupe L7.4 · effort S
Pas de test : épisode tout-NaN, graphe sans arêtes sur tout l'épisode, feature à variance
nulle, T = 1, épisode v5 à 40/41 services. Plusieurs de ces cas arriveront dans les ~720
épisodes v5.

### E11 — Hyperparamètres jamais balayés hors typing · mineur · nouveau · effort M
Les sweeps existants couvrent clustering/siamois/precursor. Jamais balayés : ε_drift, rff_dim,
fenêtres drift, d_hidden encoder, tail_size open-set. Pour les composants falsifiés (drift), on
ne peut pas distinguer « mécanisme faux » de « mécanisme mal réglé ».

### E12 — Documentation d'évaluation fragmentée · mineur · nouveau · effort S · P2
(a) Le protocole des stress tests A1–A5 n'est pas dans `docs/evaluation_protocol.md` (vérifié :
aucune occurrence) alors que c'est l'épine dorsale de l'argumentaire honnête. (b) Aucune page de
nomenclature des datasets (v3 / v4 cassé / v4_strat / rcaeval / v3_synthetic / v5) disant
lequel fait foi pour quoi.

### E13 — Limitation L7.1 (MLflow) probablement obsolète · mineur · nouveau · effort S
`mlflow` est importé dans 10+ scripts d'expériences (vérifié par grep) ; soit L7.1 (« jamais
utilisé ») est périmée et doit être mise à jour, soit les imports sont décoratifs et c'est pire.
À trancher — un document de limites qui contient une limite fausse fragilise les autres.

## 6. Plan d'évaluation v5 — trous identifiés

Le plan v5 (`docs/dataset_v5_plan.md`) est solide côté **collecte** (catalogue, sizing, held-out
2 batches, vérification pré-lancement). Côté **analyse**, rien n'est encore écrit qui engage :

1. **Protocole figé avant les données** : cible primaire Chaos Mesh/bugs F (T2), K acté (T3),
   k-fold scénario × rep (E5), PR-AUC + calibration systématiques (E2, E3) — à figer dans un
   `docs/evaluation_protocol_v5.md` *pendant* que la collecte tourne, pour ne pas adapter le

## 7. Faux positifs écartés pendant l'audit

Affirmations issues de l'exploration, **réfutées par vérification** — listées pour éviter
qu'elles ne resurgissent :

1. « Le labeling drift+injection → `normal` est un bug » — non : design documenté
   (`formalisation.md` : θ_drift n'est pas un label de régime ; `drift_flag` est orthogonal).
2. « PR-AUC jamais calculé » — faux : `chaos_mesh_target.py:35,101` (fix M-6). Le vrai point
   est E3 (non généralisé).
3. « Aucun `@hydra.main` dans le repo » — faux : `experiments/{encoder,typing,precursor}/train_hydra.py`.
   Le vrai point reste L7.2 (dualité argparse/Hydra).
4. « Zéro test sur les scripts » — faux : 2 fichiers dans `tests/unit/scripts/`. Le vrai point
   est D6 (couverture mince, v5 non testé).
5. « torch non pinné » — faux : `pyproject.toml` pinne exactement (`torch==2.11.0`,
   `numpy==1.26.4`, `scikit-learn==1.8.0`).
6. « `experiments/alerts/` sans results.md » — faux : results.md + roc_pr_curve.png existent.
   Le vrai point est E4 (pas d'IC).
7. « Aliases services jamais appliqués à Prometheus » — faux : `extractors/prom_file.py:50-57`
   transmet `aliases` au collector.
8. « Lengths SimCLR incohérentes post-padding » — faux : `collate_simclr_views`
   (`simclr.py:165-170`) calcule les longueurs post-augmentation, correctement.
9. « Normalisation d'adjacence numériquement instable (clamp 1e-6) » — faux : une ligne nulle
   donne un produit nul, pas une explosion. Le vrai point est M4 (pas de self-loops).
10. « Biais écologique TE non traité » — nuance : l'estimateur hiérarchique service-level existe
    (`causal.py:476+`) ; seul le chemin cluster-level reste pré-moyenné (M10, connu L3.2).
11. « Pas de CalibratedClassifierCV » — présent pour SVC (`model.py:89`) ; le vrai manque est
    l'évaluation de calibration (E2).
